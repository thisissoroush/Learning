# Chapter IV — Before the Interview

> *"The work you do before the interview is just as important as what you do during it."*  
> — Gayle Laakmann McDowell

---

## 🎯 Core Concept

Preparation is a skill. Most candidates "prepare" by randomly solving LeetCode problems. This chapter gives you a **structured, phased preparation plan** — what to study, when to study it, and how to build the right kind of experience before you even get a phone screen.

---

## 📋 The Preparation Timeline

```
MONTHS BEFORE TARGET START DATE
══════════════════════════════════════════════════════════
  6+ months   Build real projects. Contribute to open source.
              Learn a new language or technology. Blog.

  3-6 months  Start algorithm study. Big O first.
              Data structures: arrays, linked lists, trees,
              graphs, hash tables, heaps, tries.

  1-3 months  Daily LeetCode (1-2 problems/day).
              System design (for senior roles).
              Behavioral story preparation.

  1-4 weeks   Mock interviews with a friend.
              Review weak areas.
              Practice writing code on paper/whiteboard.

  Interview   Good sleep. No new prep. Review notes only.
══════════════════════════════════════════════════════════
```

## 🗂️ Building the Right Experience

### Projects That Signal (Resume-worthy)

```
STRONG PROJECT SIGNALS
──────────────────────────────────────────────────────────
  ✅ Multi-person projects — you collaborated + integrated
  ✅ Open source contributions — code reviewed by others
  ✅ Projects with real users — you solved a real problem
  ✅ Projects you can demo — live URL, GitHub with README
  ✅ Technologies that match target job posting

  ❌ AVOID on resume:
  ❌ Tutorial projects ("following a YouTube video")
  ❌ Class projects with no unique angle
  ❌ Projects with no README, no tests, no deploy
──────────────────────────────────────────────────────────
```

### The Power of Open Source

Contributing to open source proves:
- You can read and understand other people's code
- Your code survives review by maintainers
- You communicate in technical writing
- You know how to use Git workflows (PRs, reviews)

## 📝 The Resume

Gayle gives specific, opinionated resume advice:

```
RESUME RULES (from Gayle)
──────────────────────────────────────────────────────────
  Length:       1 page for < 10 years experience
  Format:       Plain text friendly (ATS systems)
  Bullets:      "Accomplished X by doing Y, resulting in Z"
                NOT: "Responsible for maintaining systems"

  ✅ Good:  "Reduced API latency by 40% by introducing
             Redis caching layer, improving P99 from 800ms
             to 480ms and supporting 2× user growth"

  ❌ Bad:   "Worked on backend systems and helped improve
             performance"

  Order:    Name → Links → Education → Experience →
            Projects → Skills
──────────────────────────────────────────────────────────
```

### Keywords Matter (ATS Filters)

```java
// Think of ATS as a keyword scanner
// Your resume passes through it BEFORE a human reads it

INCLUDE explicitly:
  - Language names: Java, Python, Go, TypeScript
  - Framework names: Spring Boot, React, Kubernetes
  - Concepts from job posting: "distributed systems",
    "microservices", "CI/CD", "REST APIs"
```

## 🗺️ What to Study — The Core Checklist

```
MUST-KNOW DATA STRUCTURES
──────────────────────────────────────
  □ Array / Dynamic Array (ArrayList)
  □ Hash Table / HashMap
  □ Linked List (singly + doubly)
  □ Stack
  □ Queue / Deque
  □ Tree (Binary Tree, BST)
  □ Heap (min-heap, max-heap)
  □ Trie
  □ Graph (adjacency list + matrix)

MUST-KNOW ALGORITHMS
──────────────────────────────────────
  □ BFS (Breadth-First Search)
  □ DFS (Depth-First Search)
  □ Binary Search
  □ Merge Sort / Quick Sort
  □ Dynamic Programming (memoization + tabulation)
  □ Recursion + Backtracking
  □ Two Pointers
  □ Sliding Window
  □ Topological Sort
  □ Union-Find (Disjoint Set)

MUST-KNOW CONCEPTS
──────────────────────────────────────
  □ Big O Time and Space Complexity
  □ Bit Manipulation basics
  □ Object-Oriented Design principles
  □ System Design at scale (senior roles)
```

## 🎯 Mock Interviews — The Most Underused Tool

Reading about algorithms ≠ doing them under pressure.

```
HOW TO DO EFFECTIVE MOCK INTERVIEWS
──────────────────────────────────────────────────────────
  Partner:  A friend or colleague (ideally an interviewer
            themselves). Use pramp.com or interviewing.io.

  Rules:
  → No IDE — use a text editor or paper
  → Talk out loud the ENTIRE time
  → Time yourself: 35-40 min per question
  → After: interviewer gives detailed feedback

  What to practice:
  → SAYING your algorithm before coding it
  → Handling hints gracefully
  → Catching your own bugs by tracing through code
  → Estimating complexity BEFORE being asked
──────────────────────────────────────────────────────────
```

## 💡 Key Takeaways

| When | What to Do |
|------|-----------|
| 6+ months out | Build real projects, contribute to open source |
| 3–6 months out | Master data structures and Big O fundamentals |
| 1–3 months out | Daily LeetCode, system design for senior roles |
| Final weeks | Mock interviews, review weak spots, whiteboard coding |
| Resume | Every bullet: "Accomplished X by Y, resulting in Z" |
| ATS | Include explicit technology names from the job posting |
